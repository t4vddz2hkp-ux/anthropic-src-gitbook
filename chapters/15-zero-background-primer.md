## 15.1 什么是终端程序

很多人第一次接触这类项目时，会把它想成“黑框框里运行的脚本”。  
这个理解太粗糙。

### 更准确的说法

终端程序，是运行在命令行环境中的交互式应用。  
它不一定只有一行输入一行输出，也可以有：

- 多区域界面
- 滚动消息列表
- 光标控制
- 鼠标事件
- 选择高亮
- 状态栏
- 弹窗

而这套源码中的 `REPL.tsx + ink/`，已经明显属于后一种高级终端应用。

### 一个生活化类比

- 传统终端脚本，像柜台上的号码机：按一下，吐一张纸。
- 这套终端系统，更像一个小型桌面应用，只不过窗口画在终端里。

## 15.2 什么是 CLI

CLI 是 Command Line Interface，中文通常翻译为“命令行界面”。

### 最容易误解的一点

很多人把 CLI 理解成“只能输入命令”。  
其实不是。

CLI 只说明：

- 用户通过命令行环境和程序交互
- 输入和输出主要发生在终端里

但交互形式可以很多样：

- 命令参数模式
- 交互问答模式
- 全屏 REPL 模式
- 菜单模式
- 表单模式

本项目同时拥有：

- 启动参数模式
- Slash command 模式
- REPL 持续交互模式

## 15.3 什么是 REPL

REPL 是四个单词的首字母：

- Read
- Eval
- Print
- Loop

翻成自然语言就是：

1. 读取用户输入
2. 进行求值或处理
3. 把结果打印出来
4. 继续等待下一次输入

### 为什么它很重要

如果一个系统是 REPL 式的，就意味着它不是“一次性脚本”，而是“长期运行的会话系统”。

而一旦系统是长期运行的，会马上引出一整套新的工程问题：

- 会话状态放在哪里？
- 历史消息怎么保存？
- 运行中的任务怎么显示？
- 用户中途打断怎么办？
- 模型和工具如何多轮协作？

这也是为什么本项目会长出 `AppState`、`QueryEngine`、`Task`、`sessionStorage` 这些模块。

## 15.4 什么是“模型 + 工具”的工作方式

传统程序通常是：

> 用户输入 -> 程序逻辑 -> 输出结果

而这里的程序更像：

> 用户输入 -> 模型思考 -> 模型选择工具 -> 工具执行 -> 模型继续思考 -> 输出结果

这是一种“模型驱动型执行系统”。

### 用一个例子说明

用户说：

> 帮我看一下这个项目为什么测试挂了。

系统可能会经历：

1. 模型先理解用户意图
2. 模型决定调用 `Read` 查看测试文件
3. 模型决定调用 `Bash` 执行测试命令
4. 模型根据测试输出再调用 `Grep` 搜索相关代码
5. 模型整理原因并输出说明

所以这里的模型不是只会“聊天”，而是在“调度能力”。

## 15.5 什么是 Tool

在这套系统中，Tool 可以理解为：

> 供模型调用的一项结构化能力

例如：

- 读文件
- 改文件
- 跑 Bash
- 搜索网页
- 列 MCP 资源
- 启动子代理

### 为什么不是普通函数

因为 Tool 不只要“执行”，还必须告诉系统：

- 我叫什么名字
- 我需要什么输入
- 我的结果长什么样
- 我是否只读
- 我是否可并发
- 我是否危险
- 我在 UI 里怎么显示
- 我如何做权限校验

这就是为什么 `Tool.ts` 看起来像一个“大而全的协议”。

## 15.6 什么是 Agent

Agent 这个词很容易被说得很玄。  
在这套系统里，我们可以用最朴素的方式理解：

> Agent 就是一个带有独立任务目标、独立上下文和独立可用能力的执行者。

主线程本身就是一个 agent。  
而 `AgentTool` 又可以生成新的 agent。

### 主 agent 和子 agent 的差别

主 agent：

- 面向用户
- 拥有主会话
- 管理整体对话

子 agent：

- 接收更具体的子任务
- 使用被分配的工具池
- 有时会在后台运行
- 有时会在隔离 worktree 或远程环境里运行

## 15.7 什么是后台任务

后台任务就是：

> 系统已经接收了这项工作，但不再要求主线程一直阻塞等待它完成。

在这套系统里，后台任务包括：

- 长时间运行的 Bash 命令
- 异步子代理
- 远程代理

### 为什么后台任务很重要

因为如果所有事情都阻塞在主交互界面里，用户体验会很差：

- 用户不能继续输入
- 界面会像卡住了一样
- 多个工作无法并行进行

所以 `Task.ts` 和 `tasks/` 就成了系统里很关键的一层。

## 15.8 什么是流式输出

流式输出，就是结果不是“一次性全部返回”，而是一边产生一边显示。

### 举例

不是这样：

- 等 10 秒
- 一次性返回一大段文本

而是这样：

- 第 1 秒返回一点内容
- 第 2 秒继续返回
- 如果中间有工具调用，还会先插入工具进度

### 为什么这对系统设计影响很大

因为一旦是流式的，很多地方都必须跟着变：

- UI 不能只等最终结果
- Query 主循环要支持 `yield`
- 工具执行也要支持 progress
- 任务系统要能接收中间状态

这也是为什么你会在 `query.ts`、`StreamingToolExecutor.ts`、`BashTool.tsx` 里看到大量异步生成器和流式消息。

## 15.9 什么是 MCP

MCP 是 Model Context Protocol。  
如果完全不懂它，可以先用一个不严谨但很好记的比喻：

> MCP 像“模型的外设总线”。

就像电脑可以通过统一接口接键盘、鼠标、打印机，  
模型也可以通过 MCP 接入外部能力：

- 外部工具
- 外部资源
- 外部提示词

### 为什么本项目如此重视 MCP

因为它想做的不是一个封闭工具，而是一个可扩展平台。  
MCP 正好提供了一种标准化接入外部能力的方式。

## 15.10 什么是插件

插件可以理解为：

> 对主系统行为的打包式扩展

在这套系统里，插件不只是加一个按钮那么简单，它可能带来：

- 命令
- agent
- hook
- MCP 服务器配置

这说明插件系统的设计目标，是把外部能力有组织地接进主平台。

## 15.11 什么是 worktree

如果读者没有 Git 背景，这个词会非常陌生。

### 最直白的解释

worktree 是同一个 Git 仓库的一份“额外工作副本”。

### 为什么 Agent 需要它

假设主代理正在当前目录工作，而子代理也要改代码。  
如果两者都在同一份工作区里改，很容易互相污染。

所以系统可以：

- 给子代理创建一个新的 worktree
- 让它在独立副本中操作
- 降低冲突和风险

这就是 `AgentTool` 里 `isolation: worktree` 的直观含义。

## 15.12 什么是“提示词缓存”和“上下文压缩”

这两个概念是大模型工程里的难点。

### 提示词缓存

如果系统每次都把几乎相同的大段系统提示词重新发送给模型，会很浪费。  
所以系统会努力让提示词前缀尽量稳定，以便服务端缓存命中。

### 上下文压缩

对话越来越长时，总上下文会超过模型能承受的窗口。  
这时系统就必须：

- 保留关键内容
- 总结旧内容
- 删除冗余内容

这就是 `services/compact/` 存在的原因。

## 15.13 一个零基础读者应该带着什么问题继续读后文

下面这组问题很重要：

1. 用户输入之后，先进入哪个模块？
2. 模型怎么知道自己可以调用哪些工具？
3. 工具运行过程中，UI 怎么知道该显示什么？
4. 子代理为什么能拥有自己的上下文？
5. 长对话为什么不会无限膨胀？

如果你带着这五个问题读后面的章节，理解速度会快很多。
